# Agent operability

parble can be launched, observed and stopped from a script, on native and on the web, without anyone at the keyboard (P0-T6). The switches are the same on both platforms. Natively they are flags. On the web they are URL query parameters.

Native flags accept both `--key value` and `--key=value`. `--dump-state`, `--sensors`, `--zones` and `--paused` take no value; give one with `=`. An unknown flag or a bad value prints an error and exits with code 2. Unknown query keys are ignored on the web. A bad query value logs an error and the app falls back to the defaults.

When `--screenshot` or `--exit-after` is set, the app redraws continuously even if its window never gets focus.

On macOS a window that is fully covered, on another Space or hidden is occluded, and wgpu then skips its frames: there is no swapchain texture, so Bevy skips the capture's copy and reads back an all-zero image. The render world records whether each capture's frame had a swapchain texture (`parble_render::present`, logged as `screenshot attempt N captured, presented=...`). An all-zero capture of an unpresented frame is not judged. The app logs a warning and captures again once the window presents, up to 30 attempts within the `--exit-after` grace. With `--screenshot-tick` the sim holds its tick until the capture lands, so a retry shows the same frame. A blank capture of a presented frame still fails the lit check with exit code 3.

## Exit codes (native)

- `0`: clean exit. If a screenshot was requested, it was written and shows a lit scene.
- `2`: bad flags.
- `3`: the screenshot failed. Either it never arrived, writing it failed, or it is not a lit scene.

The lit-scene check uses the same thresholds as the web smoke. More than 50 % of pixels must be non-black (max channel above 8), more than 2 % must be lit (max channel above 60), and the frame must hold more than 16 distinct 4-bit colours. The backdrop alone passes the first test and fails the other two.

## GPU device loss

A lost GPU device (WebGPU `device.lost`, a driver reset) rebuilds the renderer instead of ending the app (`crates/parble-app/src/gpu_recovery.rs`). Bevy's `RenderErrorPolicy::Recover` requests a new adapter and device, re-runs `RenderStartup` and uploads every mesh and texture again from the main world, so assets are kept there as well (`RenderAssetUsages::default()`: up to about 15 MB more heap, 8.4 MB of kit LOD meshes, 4.9 MB of playroom textures in the playroom scenes, 1.5 MB of marble maps and 0.1 MB of environment cubemaps). Bevy 0.20 leaves three things for the app to redo, and `gpu_recovery.rs` does them: the window surface is configured again against the new device; once the new renderer has drawn a frame, every mesh, image and material is marked modified and every `VisibilityRange` changed, because `RenderStartup` drops assets still waiting to be prepared (a loss while loading would leave the kit undrawn) and empties the LOD crossfade table; and the readiness tracking starts over: `pipelines.renderFrame` counts from 0, the warm-up runs again and `ready` is false until it ends. The sim, the track, the editor and the marbles live in the main world and keep running through it.

At most 3 losses within 30 s recover. The 4th stops rendering and exits the app, as a loss did before recovery existed, and `fatal` names it. A device that keeps dying never loops. Other render errors (validation, out of memory) still quit at once, as Bevy's default does, except while a rebuild is under way: Bevy still polls the lost device then, and Safari reports validation errors from a lost device, so such an error only restarts the rebuild, at most 3 times before it is fatal. The page also drops a lost device's `onuncapturederror` hook for the same reason.

On web, `index.html` logs each loss the page did not cause in `window.__parbleErrors` and counts it in `window.__parbleGpu` (`{ devices, losses, recovered, deviceAtMs, lostAtMs }`). Once the wasm has started, a loss waits for the app's verdict (`window.__parbleGpuRecovering(count)` or `window.__parbleGpuGaveUp(why)`); a loss the app never answers within 15 s of visible time is fatal. `e2e/tests/gpu-recovery.spec.mjs` covers a loss while loading and one mid-run, and `e2e/tests/fatal.spec.mjs` the bound (`make web-e2e`).

  "pipelines": {"renderFrame": 327, "total": 58, "ok": 58, "pending": 0, "stuck": 0, "failed": 0, "lastCreatedFrame": 3, "created": [], "createdTotal": 58, "recentCreated": [[3, "…"]], "waiting": [], "failures": []},
  "warmup": {"done": true, "doneFrame": 13, "endedBy": "quiet", "waitingOn": "nothing", "texturesLoading": 0, "texturesFailed": [], "loadedFrame": 0, "stuck": []},

- `ready`: the loading is over. The sim has ticked (or playback is paused, so `--paused` runs get ready at tick 0), at least 3 frames have run, and the warm-up is done (`warmup.done`): every kit texture has loaded (or failed) and the render pipeline cache has had nothing pending and created nothing for 10 render frames since. Two bounds keep it from waiting forever: a pipeline still waiting for its shader after 120 render frames is marked stuck and no longer holds it, and it ends on render frame 600 whatever is still loading or pending (`warmup.endedBy` `ceiling`), each with a logged warning. A normal load ends quietly around render frame 13. Until then every marble the sim has not released yet is drawn far under the floor (out of view, with no frustum culling), so each marble look's pipelines, in the main, prepass and shadow views, are created while loading rather than the first time that marble rolls in. `ready` stays true once set, until a lost GPU device restarts the warm-up ([GPU device loss](#gpu-device-loss)). A pipeline created later still shows in `pipelines.created`.
- `pipelines`: the render world's Bevy `PipelineCache` on the last render frame: `renderFrame`, `total`, `ok`, `pending` (queued, or waiting for a shader or shader import to load: the cache retries those errors every other frame), `stuck` (pending 120 render frames or more), `failed` (shader errors that will not be retried), `lastCreatedFrame`, `created`, the pipelines created on that frame as `label shader-path [shader defs]`, `createdTotal`, `recentCreated` (the last 24 creations as `[render frame, name]`), `waiting` (each pending pipeline's `index`, `name`, `state`, retried `error`, `sinceFrame` and `stuck`) and `failures` (`name: error`). On wasm a pipeline is created synchronously on the main thread (WebGPU's `createRenderPipeline` compiles the WGSL), so a non-empty `created` after `ready` names a frame-time stall. `e2e/first-frames.mjs` records it on every frame of a cold load.
- `warmup`: `done`, `doneFrame` (the render frame the warm-up ended on), `endedBy` (`quiet` or `ceiling`), `waitingOn` (what held it on its last frame: `textures`, `noPipelines`, `pending`, `recentCreation`, or `nothing`), `texturesLoading`, `texturesFailed` (the kit textures whose load failed, as `path: error`, each also logged as a warning: a failed texture does not hold the warm-up, so READY comes without its map), `loadedFrame` (the first render frame with every kit texture loaded) and `stuck` (the pipelines it stopped waiting for, with their errors). `e2e/safari-diag.mjs` polls these in Safari (`docs/perf/README.md`).
- `gpuRecoveries`: how many times the renderer was rebuilt after a lost GPU device ([GPU device loss](#gpu-device-loss)). The bridge sends the same count as a `gpuRecovered` event.
- `fatal` (web only, present only after one): the first fatal page error, `{ message, stack, atMs }`, from `index.html`. It is an uncaught error, a rejection thrown through wasm frames, or a lost WebGPU device that the app did not recover from (`WebGPU device lost (<reason>): <message>`, with `recovery` naming why when the retry bound ended it). Such a throw skips Rust's unwinding, so the app usually never draws another frame, `window.__parble` stops updating and `ready` never comes. `index.html` writes `window.__parbleFatal` and sets `fatal` on the last `window.__parble` itself, and the app copies it into every later one, so a READY wait should stop on `fatal` instead of timing out. `e2e/perf-gate.mjs` and `e2e/safari-repeat.mjs` do. Uncaught errors in `window.__parbleErrors` now carry their stack.
- `tick`: sim ticks in the current run (240 Hz).
- `run`: completed 10 s runs.
- `hash`: the trajectory hash of the current run so far, as 16 hex digits. It is a string because a `u64` does not fit a JS number.
- `lastRunHash`: the hash of the last completed run. A run always stops at exactly 2,400 ticks (960 in `playroom`), so for `ramp` this equals the golden hash in `crates/parble-sim/tests/golden/ramp_10s.hash` and for `playroom` the hash in `playroom_4s.hash`.
- `marbles`: one entry per marble in spawn order. Positions are in metres, rotation is a quaternion `[x, y, z, w]`, and `linvel` is in m/s.
- `track`: the metadata name of the `.parble` track loaded over the bridge (`loadTrack`), or `null`. A loaded track replaces the scenario in the live sim and its 10 s restarts. Its placements run as kit chunk colliders through the id table in `crates/parble-sim/src/track_run.rs` (kit ids, legacy aliases, and pieces with no collider yet). `loadTrack` refuses a track with any other piece id, or with overlapping kit pieces, with a `bridgeError`.
- `trackRun`: the last bridge `runTrack`, as `{ "ticks": 2400, "hash": "…" }`, or `null`. The run is headless from tick 0, so its hash does not depend on frame timing. `web/ui/src/parble-fixtures.json` records the expected `runHash` of every valid fixture track; `make web-e2e` checks it in the browser (`e2e/tests/persistence.spec.mjs`).
- `marble`: the `--marble` type, `legacy` for the P0 marble, `lineup` in the lineup scenario, `playroom` in the playroom, `mechanisms` in the mechanism showcase, or `allpieces` on the all-pieces track (and in `showcase` and `stress2000`, which run it).
- `marbleSize`: the `--marble-size` value (P5-T1).
- `shadowLights`, `shadowLightCap`: lights casting shadows this frame and the tier's cap (0 on Low, 1 on Medium, 3 on High and Ultra). `enforce_shadow_cap` in `crates/parble-render/src/playroom.rs` turns off the lowest-priority shadows past the cap in every scenario. `playroom` on High uses all 3: the moon, the big lantern and the lamp. The pale blue fill and rim lights (`crates/parble-render/src/palette.rs`) never cast shadows.
- `view`: the playroom `--view` framing, or `null` when none was given.
- `kit` (only with `--scenario kit2000`, `playroom`, `mechanisms`, `allpieces`, `showcase`, `stress2000` or `editor`): the P1-T4 renderer. `pieces`, `chunks`, `pieceTypes` (the piece types in the layout, or placed in the editor) and `drawBound` (one draw per occupied (type × chunk) × 3 LODs, plus 3 more per animated part of the type: each mechanism part is its own mesh, P2-T6; a rope arch rope is one mesh per band, 6 + 6 + 2 over the three LODs). `variants` is the number of wood variants and `variantPieces` the pieces using each (picked by a hash of the anchor cell, or of the grid index in `kit2000`). Each (type, LOD, variant) is one material, so the kit draws as `pieceTypes` × 3 × `variants` bins. `lodTriangles` per piece type and `lodBandsM`, the camera distances of the two crossfade bands. `family` and `textures` (`path`, `kind`, `state`, the loaded `format`, and the asset server's `error` when `state` is `failed`): `kind` is `wood` for each variant's base_color and orm in the device's family, or `baked` for a piece's per-LOD AO and normal PNG. A piece's baked maps load the first frame it is in the layout or placed in the editor, so `kit2000` and `playroom` fetch only their own pieces' maps and the editor fetches six more per new piece type (they stay loaded after the last one is deleted). `draws` is read from the render world each frame: `main` is the main opaque pass's kit draws (one indirect draw per (pipeline, material, mesh) bin) over `mainViews` views, `mainInstances` the LOD instances in those bins and `ditheredInstances` the ones drawn with the crossfade dither pipeline. With GPU culling Bevy keeps its multidraw bins private, so `main` rebuilds them from the view's visible kit instances. `prepass` and `shadow` are `null` when that pass's bins cannot be rebuilt (shadow cascades). `multidrawSets` counts the main pass's multidraw batch sets.
- `screenshot`: `state` is one of `none`, `pending`, `capturing`, `done` (with `lit`, `colors` and `ok`), or `failed` (with `error`).
- `camera`: the main camera this frame: `mode` (`director`, `orbit` or `fly`), `shot` (the scripted cue playing), `cuts` (hard cuts: camera mode switches only), `director` (below), `fovDeg`, `zoneOverlay` (`V`, `--zones`), `eye`, `forward` (unit view direction), `flySpeed` (m/s), `flyOnly` (the [fly-only camera](#fly-only-camera): `true` in `mechanisms` without `--camera`), the marble's screen position over the last frames (`marblePx`, physical pixels, newest first), `marbleRadiusPx`, and `post`, which holds the post components the live camera carries (`msaa`, `taa`, `ssao`, `bloom`, `dof`, `aperture`, `focusM`, `tonemapping`).
- `kit.parts` (P2-T6, only when a mechanism with animated parts is drawn): one entry per part, by anchor `cell`, `piece` and sidecar `part` index. `angleMdeg` is the angle drawn this frame, `prevMdeg` and `tickMdeg` the sim's angles at the previous and the current tick (`null` for an editor-placed piece, which has no behaviour and holds its sidecar rest angle), `alpha` the frame's interpolation factor (`angleMdeg` = `prevMdeg` + (`tickMdeg` − `prevMdeg`) × `alpha`, as for the marbles; 1 in lockstep), and `rotation` the LOD0 part's rotation in the piece frame (a chain part's top band). `segmentsMdeg` is a chain part's segment angles drawn this frame, top first, interpolated the same way (the rope arch's ropes, six each; empty for a rigid part): the renderer cuts each rope into bands at the segment joints and poses each band along them, so `angleMdeg` is the rope's pivot-to-tip chord.
- `sensors`: the sensor overlay. `on` is whether it is drawn (`--sensors`, `G`), `volumes` the sensors of every mechanism instance and `occupied` how many hold a marble at the current tick.
- `playback`: `paused` (`--paused`, `P`) and `timeScale`, the chosen time scale (`--time-scale`, `,` and `.`; kept while paused). See [Playback](#playback-pause-and-slow-motion).
- `shotCamera`: the same object captured on the screenshot frame. `shotParts` is `kit.parts` on that frame.
- `editor` (only with `--scenario editor`): see [Editor](#editor).
- `camera.orbit`: the orbit camera's `target`, `yaw`, `pitch` and `radius`.

- `camera.director` (empty outside the director): `shot`, the playing rule (`{"rule": "follow" | "frame" | "orbit" | "fixed", ...}` in metres and radians); `source`, `cue` or `zone`; `cue`, the cue index; `zone` and `zoneName`, the playing zone's index into the zone list and its name; `blend`, the blend in progress or `null` (`progress` 0 to 1, `weight`, the eased mix, `durationS`, and `depth`, the nested blends being mixed); `blends`, blends started since start; `followed`, the followed marble's index; `zones`, the zone count; `inside`, the zones the followed marble is in; `hidden`, when the followed marble is in a hidden path, its predicted `exit` and `etaS`, the estimated seconds until it comes out (distance over speed); and `clear`, whether the camera sees the followed marble past solid track this frame.
- `exited`: set when auto-exit fires.

All timing (screenshot, exit, fps) is real time in the app layer. The sim never receives wall-clock input, so none of these switches can change a trajectory hash.

## Audio and `window.__parbleAudio`

The Web Audio engine (P4-T4, `web/ui/src/audio`) runs in the HUD bundle, not in the wasm, so its state is on its own global: `window.__parble` is replaced by the wasm every frame and would drop anything added to it. Browsers only start audio after a user gesture, so the engine creates and resumes its `AudioContext` on the first pointer down, key press or touch on the page. Until then `state` is `locked` and audio frames are skipped. The SFX it plays are Paul's approved P4-T2 picks for the roll, impact and clack cues and the mechanism cues (hopper release, finish chime, checkpoint tick, splitter tick, toggle clack, gate swing, trapdoor and the three drop-hole cues), plus the tunnel rumble loop, staged into `web/ui/audio/` by `scripts/web/stage-audio.mjs` (run by `make ui-build`). Only the Ogg Opus files are fetched where the browser plays them, else the AAC fallback.

Each `audioFrame` contact and roll carries the marble's `size` (`mini`, `standard` or `shooter`), so impacts are banded by the velocity change the impulse gives that marble's real mass, and minis and shooters play their material's cues with a size pitch offset (`sizeRate` in `web/ui/src/audio/mapping.ts`). Each mechanism event carries its kit `piece` id, and `SIGNAL_CUES` there maps a piece's signal to its cue; sensor events and unmapped signals are silent. The rug cues are not staged: the sim has no rug collider (the tray and the open floor are wood slabs and report `wood`). The `blk_redirect_*` pieces are static blocks with no sensor, so a roll carries `tunnel: true` while the marble's centre is in a redirect's lower cell, the cell its tunnel runs through (`in_redirect_tunnel` in `crates/parble-app/src/audio.rs`); the engine then layers `tunnel_rumble` into that marble's roll voice with the roll's speed-driven rate, gain and low-pass, and fades it out when the flag clears. A redirect's drop entry is silent; the drop-hole cues play on the one-way hole's `drop`.

`window.__parbleAudio.stats()` returns:

- `state`: `locked`, `starting`, `running`, `suspended`, `closed` or `unsupported` (no Web Audio).
- `format` (`ogg` or `m4a`), `cues`, `files` (variants in the catalog), `fetched`, `decoded` and `loadErrors`.
- `activeVoices` (roll loops plus one-shots sounding now, never above `cap.total`), `rollVoices`, `oneShotVoices`, `tunnelLayers` (roll voices with the tunnel rumble layered in, not extra voices) and `peakVoices`. `cap` is `{ total: 24, rolls: 10 }`. Rolls keep their budget: when rolls return after one-shots filled their slots (a run restart, culled or stale rolls), the quietest one-shots are stopped and counted as `stolen`.
- `started` one-shots, `dropped` (refused: every slot held a louder voice), `stolen` (a louder one-shot or a returning roll took the slot), `rollsCulled` (rolls left silent per frame by the roll budget), `crossfades` (surface changes), `resets` (tick regressions: run restarts and loaded tracks).
- `frames`, `contacts`, `skippedFrames` (frames before the context ran), `missingBuffers`, `buffers`, `errors` and `lastError` (engine failures; the engine never throws into the HUD loop).
- `injected`: whether `inject` was used.

Pause and slow motion ([Playback](#playback-pause-and-slow-motion)): an `audioFrame` carries `"paused": true` while playback is paused (the field is left out otherwise). The engine then releases every roll loop at once and forgets the held rolls, because the tick stands still and a held roll would never go stale; listener updates continue, and a single step's impacts and mechanism cues still play. Rolls come back with the first roll sample after resuming. While paused or slowed, the app sends a frame's contacts, rolls and mechanism events only once at least 4 sim ticks (one 60 Hz roll sample) have passed since the last ones went out (`AudioPacer` in `crates/parble-app/src/audio.rs`); the frames in between carry only the tick, camera and pause flag. Slow motion therefore sends no more impact one-shots per sim second than 1x at 60 fps, and the engine holds the last roll between samples as it does at high frame rates. Rolls keep the pitch and gain of the marble's real speed.

`window.__parbleAudio.inject(event)` is a test hook: it decodes `event` like a bridge event and feeds it to the engine if it is an `audioFrame`, returning `false` otherwise. After the first injected frame, live bridge frames are ignored, so a driver can stress the engine with more marbles than any scenario has. `make web-e2e` runs both (`e2e/tests/audio.spec.mjs`).

`window.__parbleAudio.meter(reset?)` is the P4-T6 peak meter and followed-marble check (test only: nothing is connected until the first call, after the audio unlock). It taps the master output after the limiter (the engine's `DynamicsCompressorNode`) and before the `mute=1` zero gain, so it reads what the speakers would get while the page stays silent, plus the master bus before the limiter. Every fed audio frame it reads the last 32,768 samples (683 ms at 48 kHz) of each, so coverage is gapless while frames come faster than that. It returns `running`, `peak` and `peakDb` (largest absolute sample at the output, a sample peak, not an intersample true peak), `clippedReads` (reads holding a sample at or above 1.0), `prePeak` (before the limiter), `reads`, `maxGapMs` (longest time between reads) and `windowMs`, and from `window.__parble.camera.director.followed`: `focusFrames` (frames the followed marble was rolling, the engine's own audible-roll test: in contact, above the roll speed threshold, with a roll cue), `focusSilent` (of those, frames it held no sounding roll voice), `focusMarbles` and `maxRolling` (most marbles rolling at once). `reset` clears the counters. `timing(true)` records the main-thread milliseconds of every fed audio frame (the engine's consume plus the music director and player update, `performance.now()` around both) until `timing(false)`, and `timings()` returns them, at most 65,536. `e2e/tests/audio.spec.mjs` runs the meter on `stress2000`; `make web-audio-perf` (`e2e/tests/audio-perf.spec.mjs`) runs the timing. Evidence: [docs/audio/acceptance.md](audio/acceptance.md).

## Music and the mixer

The music player (P4-T5, `web/ui/src/audio/music.ts`) plays on the engine's music bus. Its cues are the loop derivatives of Paul's five Suno takes (`scripts/audio/music_loops.py`, `make music-loops`, into `audition/music-loops/`), staged by `scripts/web/stage-audio.mjs` into `web/ui/audio/music/` with `web/ui/audio/music.json`, which gives each cue's `sampleRate`, `samples`, `loopStart` and `loopEnd` (samples). A cue file is the take's intro, the loop body (its last second already crossfaded into the audio before `loopStart`) and 0.3 s of post-roll. One `AudioBufferSourceNode` per cue plays it with `loop`, `loopStart` and `loopEnd`, so the intro plays once and the body repeats gaplessly. Cues are fetched and decoded one at a time when first wanted, and at most two decoded buffers are kept.

The director (`MusicDirector`) picks a state from the audio stream and the page: `night` while paused, `run` while any marble rolls, `build` in the editor (`window.__parble.editor`) when nothing rolls, and `night` after 30 s with nothing rolling outside the editor. A new state must be wanted for 6 s before the music follows it, so ramp restarts and short pauses do not flip it. State playlists: `build` alternates `music_build_calm` and `music_build_playful` every 2 loops, `run` is `music_run_flow`, `night` is `music_night_lanterns`, `title` is `music_title` (forced only, until the P5 title screen). A state or playlist change crossfades the two sources over 4 s with equal-power curves. `?mute=1` silences it with the rest of the engine, the graph still runs.

The "Sound" button in the bottom-right corner opens the mixer: Master, Music and SFX sliders (0–100) and a Mute box (`#parble-mixer-toggle`, `#parble-mixer-master`, `#parble-mixer-music`, `#parble-mixer-sfx`, `#parble-mixer-mute`). A bus gain is the engine default (`BUS_DEFAULTS`) times the slider position squared, so 100 keeps the default mix. Settings are stored in `localStorage` under `parble.mixer/1`, and garbage or missing fields fall back to the defaults.

`window.__parbleAudio.stats()` adds `sampleRate` (the context's rate, after the first gesture), `mixer` (`master`, `music`, `sfx`, `muted`) and `music`: `cues` (in `music.json`), `forced`, `catalogError`, then once the player runs `state`, `cue`, `source` (a new id per start, crossfade or seek), `loop`, `position` (file seconds), `wraps` (loop end to loop start, for the current source), `loopStart`, `loopEnd`, `bufferDuration`, `crossfades`, `starts`, `buffers`, `loads`, `loadErrors` and `waiting`. Test hooks: `musicSeek(seconds)` restarts the playing cue at a file position, `musicForce(state | "off" | null)` pins the state (null hands it back to the director) and `musicLevel()` returns the RMS of the music bus over the last 2,048 samples, before the master gain and the mute (its analyser is connected when the player starts; 0 before that).

`e2e/tests/music.spec.mjs` (in `make web-e2e`) seeks to 1 s before the loop end three times and checks each wrap keeps the same looping source, moves the position back to the loop start and never reads silence on the music bus, then moves the mixer's music slider and reads it back after a reload. The 10-minute soak is manual: `make music-soak` (`MUSIC_SOAK_S=600`, `MUSIC_SOAK_STATE=run` by default) plays one muted loop and fails on a silent window, a restarted source or any error. Paul's listening approval of the loops is separate.

## Glow inlays

Mechanisms can carry thin light strips set into their wood (`ref-09`), lit from sim state. The checkpoint arch (`mech_checkpoint_l1`) has one: three uprights on each side face (the arch faces abut the neighbouring pieces), dark until a marble passes, then lit (0.25 s fade) for the rest of the run. It glows warm amber (owner choice, 2026-11-08).

- Sim side (`crates/parble-sim/src/inlay.rs`): a behaviour holds an `Inlay { on, since }` per strip group, calls `Inlay::set(on, tick)` from `step`, and saves it as `inlay/<i>/on` and `inlay/<i>/since` (`-1`: never switched). It rides save/restore and the mechanism hash, and never feeds physics, so trajectory hashes are unchanged.
- Render side (`crates/parble-render/src/inlay.rs`): `piece_inlays` maps a piece id to its strip groups (boxes in the piece frame) and colour preset (`InlayColor::Amber`, the default, or `InlayColor::PaleBlue` for a cool strip). The kit and the editor spawn a `GlowInlay` per group with `spawn_piece_inlays`. The app writes `InlayFrame` from `inlay_frame(&sim.mechanisms(), tick)` every frame, and `drive_inlays` sets each group's emissive (`INLAY_ON_NITS` × colour × level). The fade is a smoothstep over `INLAY_FADE_TICKS` of sim time, so a lockstep frame shows the same glow on every run.
- Reuse: add a strip table and a `piece_inlays` entry, light the group from the behaviour, and the rest follows. A strip on a moving part (stepper slats) is a `GlowInlay` spawned under that part's entity, in the part frame.
- An editor-placed piece has no behaviour, so its inlay stays dark.

Each checkpoint pass also reaches the HUD as a `split` bridge event (`{ tick, instance, marble }`), shown as the run time in seconds per pass (`split cp1  0.546 s  marble 2`), cleared when the run restarts.

## Camera controls

Every scenario, `kit2000` and `lineup` included, has a free-fly camera (`Fly` in `crates/parble-render/src/camera.rs`). It works the same natively and on the web. On the web, click the scene first so the canvas has keyboard focus.

| Input | Effect |
|---|---|
| `F` | (Not under the [fly-only camera](#fly-only-camera).) Enter fly from the current view and lock and hide the cursor (pointer lock on the web). In fly, `F` returns to the camera it replaced and releases the cursor. |
| `Esc` | Leave fly, back to the director (or orbit), and release the cursor. The director snaps straight back to its current shot (a mode switch is the one hard cut). On the web the browser also releases pointer lock on `Esc`. |
| `W` `A` `S` `D` | Forward, left, back, right along the view. |
| `E` or `Space`, `Q` or `Shift` | Up, down (world Y). |
| Mouse | Look (yaw and pitch) from raw mouse motion while the cursor is locked. If the lock is refused, left or right drag looks instead, from cursor movement. |
| Wheel | Fly speed, ×1.25 per line, 0.02 to 5 m/s (starts at 0.3 m/s). |
| `C` | Director and orbit toggle (ignored while flying). |
| `G` | Mechanism sensor overlay on or off, in every camera mode (see `--sensors`). |
| `V` | Camera zone overlay on or off, in every camera mode (see `--zones`). |

The camera moves only on input and uses real time, so it keeps working while `--lockstep-after` holds the sim. With no input it never leaves the director, so `--screenshot`, `--exit-after`, `?screenshot=` and `window.__parble` runs frame exactly as before. Keys typed into the HUD (the Import, Export, Run and Save controls) stay there, because the browser only delivers keys to the canvas while it has focus. The HUD shows the controls in its bottom-left line. `make web-e2e` drives the fly camera with the keyboard and mouse in GPU Chromium (`e2e/tests/flycam.spec.mjs`).

### Fly-only camera

`--scenario mechanisms` without `--camera` starts in fly (`FlyOnly` in `crates/parble-render/src/camera.rs`, `CameraChoice::FlyOnly` in `crates/parble-app/src/agent.rs`) at the eye and look point of `Cues::mechanisms`' opening row shot, and the director never runs. The camera stays still until moved: `W` `A` `S` `D`, `Q`/`E` (or `Shift`/`Space`) and the wheel as above, and left or right drag looks, without pointer lock. `F`, `Esc` and `C` do nothing, so no key hands the camera to the director or the orbit. `window.__parble.camera` reports `mode` `fly` and `flyOnly` `true`, and the HUD's controls line drops `F/Esc back`. `--camera director` (`?camera=director`) restores the director and its cues; it is not the default for a person.

## Camera director and zones

The run camera is a director (`crates/parble-render/src/director.rs`, PRD §5.6). Each frame it picks a shot, evaluates it into a pose (eye, view direction, field of view, DoF focus distance) and blends between shots. It reads the marble positions the app copies out of the sim each frame and never touches the sim, so no hash or golden changes.

Shot rules:

- `follow`: the tracking shot. It frames the marble's action window: its path over the last 0.25 s, its look-ahead along its velocity for 0.5 s, and any mechanism near that path (`CameraInterest`, the mechanism cells of the track). The look point and the DoF focus sit on the window's centre, ahead of the marble, and the camera pulls back from its closest (140 mm behind, 70 mm up) to fit the whole window, at most 0.9 m. Its bearing follows the window's chord, so it starts turning before a corner and averages out a switchback. The yaw turns with a 0.7 s response, never faster than 0.85 rad/s and never accelerating faster than 2.5 rad/s², so a 90° rail curve that turns the marble at 5.6 rad/s turns the camera at most 0.88 rad/s (1.90 rad/s² peak yaw acceleration, `director::tests::a_corner_does_not_whip_the_follow_camera`). The fit measures each window point in the view's own basis, so a path running away from the camera, which the view foreshortens, costs little distance.
- `frame`: pull back and fit a target with the marble: the marble alone, a point, or a vertical axis segment (a drop or a future helix). The axis stays centred and the distance follows the marble, never faster than 1 m/s, so the whole segment and the marble stay in view. The view looks down at a set elevation, from a set bearing or from the bearing the camera had when the shot began. Focus goes to the marble or the target.
- `orbit`: circle a point at a radius and height, starting from the camera's current bearing.
- `fixed`: a fixed eye and look point (the scripted `fixed` and `set` cues are fixed rules).

Blends: every shot change blends, whether it is a cue change (0.8 s), a zone entry or exit (the zone's blend-in and blend-out), a change of followed marble, or a run restart (1 s each). The eye is interpolated, the view direction's bearing (the short way round) and elevation interpolated apart, so a blend between views facing apart turns level instead of tipping over the top, and the field of view and focus distance interpolated, with a smootherstep weight. Both sides stay live during a blend. A blend that starts during another keeps the one in flight as its source (three deep, after which the oldest freezes), and a restart freezes the outgoing view first so the teleported marble cannot drag it. The only snaps are the director's first frame and a camera mode switch (`C`, `F`, `Esc`).

Zones: a zone is a trigger volume, either an axis-aligned box or a vertical cylinder, with a shot rule, a priority, blend-in and blend-out times and a hold. The followed marble is inside until it is 8 mm past the boundary, and a zone stays active for its hold after the marble leaves (at least 0.15 s), but only while the camera still has the marble in frame: a marble that leaves the frame ends the hold at once and the shot blends back. The active zone with the highest priority wins, and ties go to the earlier zone. With no zone active the scenario's cue plays. The followed marble is the moving one: in normal play one marble moves at a time. When several move, the director keeps the current marble while it moves and for 1 s after it stops, then moves on to the first moving marble.

Where zones come from (`crates/parble-app/src/zones.rs`):

- Authored zones in the track model: `Track::camera_zones` (`crates/parble-core/src/camera_zone.rs`), saved as the optional `camera_zones` list of a `.parble` file. The list is left out when empty, so older files load and save byte for byte, still as schema 1. Units are integer µm, millidegrees, permille and ms, and `ParbleFile::validate` checks each zone. The editor UI that places zones is not built yet (P3-T5). It edits them through `Track::camera_zones` like placements.
- Piece hints (`camera_zone::piece_hint`): `mech_checkpoint_*` gives a short framing beat on the arch (a box over its cells, held 0.9 s), and `blk_redirect_*` and `blk_tower_*` frame their cell column's axis (a cylinder). Hints have priority 1, below authored zones. A future helix declares its axis zone by adding its id prefix to `piece_hint` as `CameraHint::Axis`. `hint_zones` then builds the cylinder over the helix footprint's column and frames its axis from the lowest cell floor to the highest cell top.
- The `allpieces` demo zone (`zones::allpieces_demo`): a cylinder round the drop at cell (24, 3, −7) into the tower socket below it. It frames the column's axis with the marble, focused on the axis, at priority 10, blending in over 0.8 s, holding 0.8 s and blending out over 1.4 s. The cylinder's radius is 90 mm and the shot looks down at 30°. Marble 0 enters it at tick 1284 and the zone ends at tick 1568 (`zones::tests::the_first_marble_drops_through_the_demo_zone`).

Hidden paths: pieces that hide the marble (`blk_drop_*`, `blk_redirect_*`, `blk_tower_*`, `mech_hole_oneway_*`; `zones::hides_marble`) are hidden paths. `zones::obstacles_for` reads each one's box from its cells and its exit from the piece's `Out` port in the track graph: the port's cell and face, at the port's channel floor for a side port. While the followed marble is inside one, the follow shot's action window reaches to the exit, its heading turns towards the exit, and its springs drop the marble's velocity lead, all through the follow yaw limits, so the camera pulls back and turns to hold the way in and the exit together before the marble comes out. Its line-of-sight check (below) then tests the exit and a point just outside it instead of the hidden marble.

Line of sight: `zones::obstacles_for` also makes the cells of every vertical run of two or more occupied cells in one cell column solid, one box per cell inset 4 mm (the tower, pillar stacks, a block over a rail). The marble's own cell never blocks, but the block above it does: on `allpieces` the marble leaving the tower socket runs through `rail_joint_l1` under `blk_straight_l2`, an open-sided rail that is not a hidden piece, and the camera has to see it from the side rather than through the block. With these solids and the follow shot keeps the marble in view past them. Each frame it tests the marble and its look-ahead (0.25, 0.5 and 1 s ahead) from the view it is heading for and from its current bearing. When those are blocked it takes the cheapest clear move from `CLEAR_VIEWS`, which tries swinging round before rising, and never looks down more steeply than 60° (`FOLLOW_MAX_ELEVATION`), escalates while its own lagging eye is still blocked, and returns to the plain view once that has been clear for 0.5 s. The rise eases through the same response, rate and acceleration limits as the yaw, and the swing goes through the yaw limiter itself. Framing shots with a set bearing only rise (`FRAME_LIFTS`); those that took their bearing from the camera may also swing (`FRAME_VIEWS`), but a swing of a radian or more rises with them, so the frame looks down over its target from the far side rather than across the track side-on, and the low far swings come last. A blend mixes two clear views into one that need not be clear, so during a blend the director also checks the mixed pose and, when it looks through solid track, swings it up about the marble's depth (`FRAME_LIFTS`, the same limits). Inside a hidden path the marble is meant to be out of sight, so the check does not apply to it. This is read-only: the solids and hidden paths come from the track model, never from the sim.

Tests: `director::tests` bounds the per-frame camera change during cue blends, zone entries, exits and re-entries, retargets and restarts. It checks that a 90° corner keeps the yaw rate under 1 rad/s and the yaw acceleration under 3 rad/s², that the follow look point leads the marble on a straight, that an axis framing keeps both ends and the marble inside the frame, and that zones resolve by priority and hold. `a_hidden_path_puts_its_exit_in_view_before_the_marble_reappears` drops a marble through a shaft that turns it 90°: on the frame it reappears the exit projects inside the frame, and the peak yaw rate stays under 1 rad/s. `a_tall_piece_never_hides_the_followed_marble` puts a 0.3 m column where the plain follow view of a corner looks through it: the plain view sees the marble in 88.8% of frames, the avoiding view in 96.4%, with peak yaw 0.75 rad/s and pitch 0.48 rad/s. On the whole `allpieces` run (`zones::tests::the_allpieces_run_keeps_the_marble_in_sight`) the marble is in sight in 95.1% of frames outside hidden paths, against 92.1% without avoidance. `zones::tests::the_tower_zone_keeps_the_marble_in_frame` checks that on every frame the tower drop zone plays, outside hidden paths, the followed marble is in frame, and that no view on the run looks down more steeply than 60°. The one exception is the second after the director moves on to a new marble already at the tower, whose blend starts from the old marble's view.

## Playback: pause and slow motion

The live sim can be paused, stepped and slowed in every scenario, the editor's run and a loaded track included (`crates/parble-app/src/playback.rs`). The sim step never changes: `advance_sim` in `crates/parble-app/src/main.rs` scales the real time it feeds the fixed-step accumulator (`frame_ticks`), so a run at any time scale, or one paused and resumed, reaches the same tick-for-tick trajectory and the same hashes and goldens. The bridge's headless `runTrack` is not affected.

| Key | Effect |
|---|---|
| `P` | Pause or resume. Paused, no ticks run and the accumulator is kept, so the frame freezes exactly where it was and resuming does not jump. |
| `,` | Slower: 1 → 0.5 → 0.25 → 0.1 (stops at 0.1). Works while paused. |
| `.` | Faster: back toward 1 (stops at 1). Works while paused. |
| `N` | While paused, run one step of 4 ticks (1/60 s, one 60 Hz roll sample). Ignored while running. |

The keys are ignored while Ctrl or Super is held (browser print and preferences). On the web, click the scene first. The camera (director, orbit, fly), the sensor overlay (`G`), the HUD and the editor keep working while paused or slowed: they run on real time, not on sim ticks. The HUD readout appends `  paused` and the time scale (`  0.25x`) only when they apply, so at 1x it stays `fps N  tick N`; the bridge `frame` event carries `paused` and `timeScale` only when not the defaults (bridge protocol 3). Its bottom-left controls line lists the keys.

With `--lockstep-after`, pause and `N` apply but the time scale does not: lockstep advances exactly 4 ticks per frame, and a scaled lockstep frame would not be a whole tick count.

Tests: `playback::tests` (`a_quarter_speed_run_reaches_the_golden_hash_in_four_times_the_frames`, `every_time_scale_reaches_the_golden_hash`, `a_paused_stepped_and_resumed_run_reaches_the_golden_hash`) drive the ramp run through `frame_ticks` one 60 Hz frame at a time and check the golden `ramp_10s` hash. `make web-e2e` presses the keys in GPU Chromium (`e2e/tests/playback.spec.mjs`).

## Editor

`--scenario editor` (P3-T4, `crates/parble-app/src/editor.rs`) edits a track of kit pieces through the P3-T1 commands, with undo and redo. The palette is every builtin kit piece (the 34 sidecars in `assets/kit/`, one list in `parble_kit::builtin_piece_ids!`), in id order: blocks, mechanisms and rails, multi-cell footprints included, with each mechanism's animated parts drawn at their rest pose (a placed mechanism has no behaviour until a `run`, `stop` or `reset` rebuilds the sim; a loaded track's mechanisms run theirs, and their parts move with the sim). The brush starts on `blk_straight_l3`. The `fill` layout keeps to the four one-cell P1-T4 showcase blocks (`blk_straight_l3`, `blk_curve90_l3`, `blk_slope_gentle_l3`, `blk_end_l3`). The editor UI overlay (P3-T5) is described below. A `loadTrack` or `runTrack` in this scenario restarts the live sim on the loaded file, and the editor starts over on that track: its placements become the editor's pieces, the selection is cleared and the undo and redo history is reset (the loaded track is the new base, so undo cannot reach edits from before it). `runTrack` therefore also discards edits made since the load. The overlay's Library saves and exports the edited track through the `export` op. A loaded track does not restart every 10 s in the editor, so edits after a load keep their incremental colliders.

Every command, undo and redo diffs the placements by anchor. Only the changed placements are removed and placed in the live sim's chunk colliders, and only the render chunks holding their anchors are respawned. Dirty colliders are rebuilt in stages (gather, simplify, tag, install), as many as fit 4 ms a frame. A dense 64-piece chunk is about 17 ms of work natively, so one chunk spreads over a few frames instead of stalling one. `crates/parble-sim/tests/incremental_edit.rs` checks that 400 random edits (mirrored curves and rails included), rebuilt in place and in stages, leave exactly the colliders a fresh build of the final track has: the same trimeshes, active contact hooks and contact-hook tags (stitched edges, channel bends, channel slopes, rail arcs). An edit dirties the chunks of the pieces across its cells' faces, edges and corners, since a stitched edge on a cell corner looks up the diagonal cell.

### Nudge zones

`Track::nudge_zones` (`crates/parble-core/src/nudge_zone.rs`, omitted from the `.parble` file when empty) are invisible boxes that top a marble up to a minimum speed along a heading while its centre, quantized to 1 µm, is inside. `parble-sim` applies them every tick before the physics step (`crates/parble-sim/src/nudge.rs`): for each marble in spawn order and each zone in track order, when the speed along the zone's unit direction `(cos p · cos y, sin p, −cos p · sin y)` (libm) is below `min_speed_um_s`, the velocity gains `min(max_accel_um_s2 · dt, shortfall)` along it. A marble at or above the minimum is untouched, and nothing is added sideways. That is the default top-up mode. A zone with `"mode": "constant"` instead adds `max_accel_um_s2 · dt` along the direction to every marble inside, every tick, whatever its speed (`min_speed_um_s` is kept but unused). The file omits `mode` when it is top-up, so files from before it load and save byte for byte; no schema or physics version bump. Defaults: 0.2 m/s and 1 m/s² (gravity on a 1-in-10 incline, 4.2 mm/s per tick); the file caps both at 2. With no zones the pass is skipped, so every existing golden holds and `PHYSICS_VERSION` is unchanged. Every edit hands the zones to the live sim for its next tick, and the marble check builds its runs through `TrackRun`, so it sees them. Tests: `parble_sim::nudge::tests` (six rope arches stall every marble, a zone over them finishes all three; the marble check's stall warnings clear), `tests/golden_nudge_track.rs` (golden `nudge_track.hash`, also checked in wasm by `make determinism-wasm`), and the `nudge-zones` fixture's run hash in `web/ui/src/parble-fixtures.json`. Constant mode: `a_constant_zone_keeps_accelerating_past_the_minimum_where_top_up_stops` (from rest, top-up holds 0.2 m/s while constant reaches 1 m/s in a second), the constant track's golden `nudge_constant_track.hash` (also in wasm), and the `nudge-zones-constant` fixture.

`window.__parble.editor.nudges` holds `count`, `selected` (the selected zone's index, or `null`) and `zones` (the first 64, in track order): each zone's `index`, `name`, `mode` (`"top_up"` or `"constant"`), `minUm`, `maxUm`, `yawMdeg`, `pitchMdeg`, `minSpeedUmS`, `maxAccelUmS2`, `cell` (the cell holding its centre), `outline` (the box's 8 corners in canvas pixels, x/y/z bit order, or `null` off screen) and `arrow` (the heading arrow's projected tail and head, or `null`), refreshed every frame. The engine draws nothing: the overlay draws the outlines and arrows in their own SVG layer, `#pe-nz`, (pale blue, the selected zone brass) only while no run is active or building, so a run and every capture show no zone. The overlay's Nudge zones block (under the marble check) lists the zones with Select and has Add zone, over the selection or the cell at the orbit target. Add zone and a row's Select also switch to the Select tool, so `R` turns the zone rather than the brush. The selected zone's inspector (Selection) steps its size a cell per axis, moves it a cell or a level, turns its heading 45° and tilts it 15°, sets its Mode (a Top up / Constant segmented radio), and steps the minimum speed 0.05 m/s (hidden in constant mode, where it is unused) and the push 0.25 m/s², each one `nudgeSet`. `e2e/tests/editor-ui.spec.mjs` drives all of it, with the export and a run, and writes `docs/design/editor/built-nudge-zone.png`.

### Marble check

`check` runs the release once per marble spec in `parble_sim::marble_check::check_kinds`: cat's eye (standing for swirl, onionskin, opal and glow, which share its physics and so its outcome), glazed and steel, each with every queued marble spawned as that type. The sim is deterministic, so the result is exact for that release: native and wasm give the same report (`crates/parble-sim/tests/golden/allpieces_marble_check.txt`, checked natively and by `make determinism-wasm`). Per marble the outcome is `Finished` (a cup counted it), `FellOff` (its centre went below −60 mm, below the lost line, or onto the tray floor over no placement's footprint; reported at the placement it entered last) or `Stalled` (on the track and in no cup when the check ended; reported at the placement holding it, and flagged as still rolling when it was at 5 mm/s or faster). Once every marble is out, a check ends when each marble finished, fell off or stayed under 5 mm/s for 2 s, else at the cap: 12 s after the last release and never before 30 s (5 min at most). The cap gives the all-pieces release its 30 s run, so the check reports what `allpieces.rs` pins for every type and size (`the_marble_check_reports_the_pinned_outcomes`). The check is built and run one `MarbleCheck::step` unit at a time (a `TrackRunBuild` unit, then 8 ticks), as many units a frame as fit under `CHECK_BUDGET_MS` (4 ms; a unit starts only while the longest unit so far fits), and it waits while a `run`, `stop` or `reset` builds. Any edit, a loaded track included, stops a check under way and marks a finished one stale; it never reruns by itself.

`window.__parble.editor.check` holds `state` (`none`, `running`, `done`, `stale` or `failed`), `progress` (0 to 1), `current` (the type and size running), `release` (`release`, `intervalTicks`, `marbles`, `seed`, `sizes` and `allSizes`: what the panel names), `edits` (the edit count it checked), `runs` (per spec and size: `marble`, `also` (the types sharing its spec), `size` (`null` for the queue's own mixed sizes), `marbles`, `finished`, `fellOff`, `stalled`, `ticks`), `warningCount`, `warnings` (the first 32, grouped by type, size, outcome and placement: `kind` (`fellOff` or `stalled`), `marble`, `also`, `size`, `piece`, `anchor`, `cell`, `marbles` (release order), `rolling` (of a stall's marbles, those still rolling at the end) and `tick`), `error` and `timing` (`frames`, `workMs`, `frameMsMax`, `unitMsMax`, `wallMs`). The warnings are a list parallel to `issues`, never validation issues: `issueCount` and "Track is complete" ignore them. The panel lists them under the issues with the same Show, and also counts a result stale once the Run release differs from the one it checked.

`e2e/tests/editor.spec.mjs` (in `make web-e2e`) places 50 pieces with the real mouse and checks the ghost, picking, slicing, box select and a move drag. It also checks that a mirrored curve renders like the unmirrored curve of the same shape in the same cell (mirrored pieces draw reversed-winding LOD meshes, since the negative x scale would otherwise cull their outside), and that `loadTrack` and `runTrack` start the editor over on the loaded track. `make web-editor-perf` runs `e2e/tests/editor-perf.spec.mjs`, the 2,000-piece edit frame-time trace, into `target/perf/p3t4-editor.json`, and its second test times four Run and Stop presses on the same fill into `target/perf/p3t5-run-build.json` (worst rAF frame, round trip and the whole `lastRun`), failing while the worst frame is over budget. It waits for the 1-minute load average to reach 15 or less and reports the sample as not taken when it does not.

The browser suites are local only and never run in CI. `e2e/` has its own package, pinning `@playwright/test` 1.64.1. Install it with `make e2e-deps`. Chromium launches with `channel: 'chromium'` and the platform GPU flags (`--use-angle=metal --enable-gpu --ignore-gpu-blocklist` on macOS). `PW_GPU=swiftshader` opts into the CPU renderer.

`make web-e2e` has Playwright start `e2e/static-server.py` on 127.0.0.1:5311 over `target/web-dist/` and stop it afterwards. Every browser run (the Playwright suites, `e2e/web-smoke.cjs`, `scripts/audio/audition-smoke.cjs`) takes its Chromium flags from `e2e/gpu-args.cjs`: the platform GPU (Metal on macOS) by default, SwiftShader only with `PW_GPU=swiftshader`. Playwright's global setup (`e2e/gpu-setup.mjs`) reads the WebGPU adapter and the WebGL renderer first and fails the whole run if there is no adapter or SwiftShader shows up without the opt-in. The URL switches can be tried by hand on any served build, for example `http://127.0.0.1:5310/?quality=low&dump-state&exit-after=5`.
